# 工作文档保存（pharah-doc）

将用户明确交由本 skill 管理的文档保存到本机配置的工作目录，按功能/需求分组管理，并在后续修改时直接定位文件、避免重复询问。

## 核心常量

- **共享配置文件**：[`config.json`](./config.json)（随仓库同步，配置索引文件名、文档类型、类型模板、文档格式和日期格式）
- **本机配置文件**：`config.local.json`（不纳入版本控制，只保存本机工作文档根目录；结构参考 [`config.local.example.json`](./config.local.example.json)）
- **索引文件**：`<本机工作文档根目录>/<config.json 中的 workDocs.indexFile>`（记录“功能/需求 → 文件夹/文件”的映射，默认 `README.md`）
- **文档类型与模板**：[`doc-type/`](./doc-type/)（为每种文档类型维护 Markdown 和 HTML 参考模板）
- **版本规则**：新文档从 `1.0.0` 开始；每次修改递增补丁版本号，例如 `1.0.0` → `1.0.1`。
- **变更日志**：每个主题目录维护 `update.log`，记录该目录内文档的创建与修改。

## 触发条件（何时启用本 skill）

仅当用户显式调用 `pharah-doc`（例如通过技能选择器调用，或明确说“使用 pharah-doc”）时启用。

仅提到文档、要求生成文档或提及 `pharah-doc`，但未显式调用本 skill 时，不触发此流程。

## 工作目录配置

1. 开始任何操作前读取共享 `config.json` 的 `workDocs.indexFile`。除非用户为当前操作明确指定了完整路径，否则还需读取本机 `config.local.json` 的 `workDocs.rootDirectory`。
2. 首次显式调用本 skill 时，如果本机配置文件不存在或根目录未配置，先提示用户配置工作文档根目录，并通过 `init/初始化` 流程收集路径；配置完成后再继续用户请求的操作。不要自行推测或恢复旧的硬编码路径。
3. 用户只为当前文档操作指定其他完整路径时，仅本次操作使用该路径，不修改本机配置。用户明确要求更改默认工作目录时，更新 `config.local.json`。
4. 路径必须是绝对路径。首次配置时，若用户确认的目录尚不存在，可在确认其父目录可访问且可写后创建；已配置目录后来不存在、不可访问或配置内容格式错误时，明确说明问题并请用户修正。不要静默回退、自动切换目录或自动迁移旧文档。
5. `config.local.json` 已加入仓库 `.gitignore`；不得移除忽略规则或将其中的本机路径复制到共享配置、示例文件或仓库 README。

## 指令

仅在用户显式调用本 skill 后，根据用户表达识别指令。以下关键词是常见表达，不要求固定命令格式：

| 指令 |
|------|
| **Init / 初始化**：`init`、`initialize`、`setup`、初始化、初始化配置、配置工作目录。设置或重新设置本机工作文档根目录。首次调用且本机目录未配置时，先提示用户输入绝对路径；用户可直接提供路径。确认路径可访问后，将其写入本机 `config.local.json` 的 `workDocs.rootDirectory`，保留其他配置。目录不存在时先征得用户同意再创建。单独初始化后报告配置结果；若首次初始化时同时提出其他指令，初始化完成后继续处理。更改目录不自动迁移、复制或删除旧目录文件。 |
| **Create / 创建**：`create`、`add`、`new`、`generate`、`write`、创建、新建、新增、生成、编写。按后续流程选择类型、格式和模板创建文档；版本从配置的初始版本开始，并更新索引和 `update.log`。 |
| **Read / 读取**：`read`、`view`、`show`、`find`、`search`、`get`、`list`、读取、查看、查阅、查找、查询、列出。按索引定位并读取或展示文档；保持只读，不修改版本、索引或 `update.log`。 |
| **Update / 更新**：`update`、`edit`、`modify`、`revise`、`change`、更新、修改、编辑、补充、完善。编辑目标文档，递增版本，并同步更新索引与 `update.log`；具体流程见“后续文档修改”。 |
| **Delete / 删除**：`delete`、`remove`、`drop`、删除、移除、废弃。执行前必须确认目标文档及其路径；确认后删除文件、从索引中移除对应链接，并在主题目录 `update.log` 追加删除记录。默认不删除主题目录或其他资料。 |
| **Commit / 提交**：`commit`、提交、提交文档。仅当工作文档根目录位于 Git 工作树中时执行，否则说明原因并停止，不初始化仓库。检查当前分支、工作区和暂存区，仅提交本次文档相关的明确文件路径（文档、索引、`update.log`）；不得使用 `git add .` 或 `git add -A`。若目标文件已有预暂存变更或归属不清，先说明并请求用户处理，不重置或取消暂存；工作文档根目录外的暂存变更不得带入。提交说明使用 `doc:1.[新增]xxx文档。2.[修改]xxx文档。3.[删除]xxx文档。` 格式，仅列实际操作，编号连续，使用实际文件名及扩展名；索引和日志作为相应文档变更的一部分，若仅变更索引或日志则准确描述。显式暂存并核对差异后提交；失败时报告错误，不丢弃改动。成功后报告哈希和提交说明；无文档变更时告知无需提交。 |
| **Push / 推送 / 同步**：`push`、推送、同步、推送到远端。检查工作文档根目录所在 Git 工作树、当前分支及 upstream/remote。若有未提交文档变更，提示先执行 `commit/提交`，不得自动提交。无 upstream 或 remote 不可用时，请用户指定目标，不猜测、不修改跟踪配置。检查待推送提交；若包含无关提交，列出并询问用户确认。只推送当前分支到已配置或用户确认的目标；禁止 force push，不推送其他分支或 tags。失败时报告错误，不改写历史或切换 remote；无待推送提交时告知远端已是最新。 |

若用户只是在讨论关键词、目标文档不明确，或无法判断其意图，不要执行变更，先澄清。删除始终需要确认具体文件；Git 提交/推送仅在用户明确要求时执行。

## 流程

### Step 1 — 解析工作目录并定位或确认分组文件夹

先按“工作目录配置”解析工作文档根目录和索引文件，再按**分类 → 功能 / 需求**分组，分类沿用索引当前结构：

- `业务项目/活动与功能`：活动、玩法、功能需求及其设计、接口、测试、配置和初始化脚本。
- `业务项目/支付与钱包`：支付渠道、支付改造/迁移、首充、钱包等支付及资金相关需求。
- `研发资产/规范与技能`：通用编码规范、开发约定、可复用技能及其参考资料。
- `研发资产/工具与配置`：通用开发工具、数据库连接配置和环境配置。
- `工作记录`：工作日志、问题排查等不归属单一项目的过程资料。

1. 先读取 `<工作文档根目录>/<workDocs.indexFile>`（若存在），判断本次文档所属的功能/需求是否已有对应路径。
   - **已有** → 直接复用索引中的分类路径和文件夹，不必再询问文件夹名称。
   - **没有** → 先按资料所属的长期业务主题归入最匹配的现有分类；同一需求的说明、脚本、测试和配置资料放在同一主题目录，不按文件类型拆分。向用户确认新文件夹名称（如“订单模块”“登录需求”“XX方案”）；分类或归属不明确时一并确认。
   - 只有资料明显无法归入现有分类时才新增分类，并先与用户确认分类名称和放置位置。
2. 目录名使用清晰、稳定的业务/需求名称，优先沿用现有项目或需求名称。目标路径 = `<工作文档根目录>/<分类路径>/<文件夹名>/`。文件夹不存在则创建。

### Step 2 — 确定类型、格式和文件名

1. 读取 `config.json`，根据文档用途选择已配置的文档类型和对应模板。类型或用途无法明确判断时，先询问用户；不得静默使用不匹配的模板。
2. 用户明确指定了文档格式时使用该格式；未指定时使用配置中的默认格式。只允许使用配置中启用的格式。
3. 使用以下命名格式：`主题_文档类型_创建时间.文档格式`。
   - **主题**：默认使用主题目录名；若用户创建主题目录时指定了主题名称，则使用该名称。
   - **文档类型**：使用配置中的类型名称，例如 `调研文档`、`设计文档`、`DDL文档`、`开发文档`、`接口文档`。
   - **创建时间**：使用配置的日期格式，当前格式为 `YYYYMMDD`。
   - **文档格式**：使用小写文件扩展名，例如 `.md`、`.html`。
   - 示例：`订单模块_设计文档_20261016.md`。
4. 按选定类型和格式读取配置所指向的模板，以完整文档内容替换模板占位内容；不要把占位符原样留在最终文档中。新文档版本设为 `config.json` 中的 `versioning.initialVersion`。
5. 写入主题目录。若同名文件已存在，**先向用户确认是否覆盖**，得到确认后再写入。
6. 在主题目录的 `update.log` 追加创建记录，按配置的 `changeLog.entryFormat` 每条一行，包含日期、文档名、初始版本和简要变更说明。日志使用 UTF-8 文本，首次创建时写入简短标题；后续只追加，不覆盖既有记录。日志本身不作为版本化文档。

### Step 3 — 更新索引

在 `<工作文档根目录>/<workDocs.indexFile>` 对应分类下新增或更新主题记录，保持现有分组结构，并列出文档版本及主题目录、文档和变更日志的可点击链接：

| 功能/需求 | 文件夹 | 文档与资料（版本） |
|-----------|--------|--------------------|
| 示例功能 | [示例文件夹](业务项目/活动与功能/示例文件夹/) | [示例文档](业务项目/活动与功能/示例文件夹/示例文档.md)（`1.0.0`）；[变更记录](业务项目/活动与功能/示例文件夹/update.log) |

- 索引链接使用相对于索引文件所在根目录的 Markdown 链接，不使用绝对路径；链接文字简短且能说明目标内容，目录链接以 `/` 结尾。
- 每篇文档在索引中标注其当前版本；创建或修改文档后，同步更新索引中的版本号。
- 链接目标必须与磁盘上的实际目录或文件一致。新增、重命名、移动或删除资料时，同步修正索引链接及受影响文档中的旧路径。
- 链接路径中的空格编码为 `%20`，左右圆括号分别编码为 `%28`、`%29`；其他 URL 特殊字符也进行百分号编码。中文和普通文件名字符可直接保留。
- 若配置指定的索引文件不存在，则先创建，并按上述分类/链接规则建立结构。
- 每次保存/修改后保持索引与磁盘一致；完成前检查相关链接可解析到实际目标，并检查 Markdown 链接语法。

### Step 4 — 后续文档修改（不再追问）

当用户后续在本会话（或后续会话）中要求**修改 / 更新 / 补充**某份已保存的文档时：

1. 读取配置指定的索引文件，按功能/需求或文档名定位到对应文件路径。
2. 读取文档当前版本。每次对文档内容进行修改，都按 `config.json` 中的 `versioning.incrementOnUpdate` 递增版本号；当前规则为只递增补丁位，例如 `1.2.3` → `1.2.4`。同步更新文档内的版本号、索引中的版本号，并在所在主题目录的 `update.log` 追加日期、文档名、新版本和简要变更说明。
3. **直接修改该文件**，不再询问“是否保存/保存到哪/文件夹叫什么”。
4. 若文档尚无版本号，将当前版本视为 `config.json` 中的初始版本号，并在本次修改后按规则递增；若版本号格式异常，不要猜测，先询问用户。
5. 若索引中找不到对应记录，再向用户确认目标文件或是否新建。

修改已保存文档时保留其现有文件名；只有用户明确要求重命名时才按当前配置重新命名，并同步更新索引链接。

## 注意事项

- 工作文档根目录从本机 `config.local.json` 读取；索引文件名从共享 `config.json` 的 `workDocs.indexFile` 读取。
- 首次调用时若本机目录未配置，先完成初始化，再继续 CRUD 操作；用户显式调用 `init/初始化` 时允许重新配置目录。
- 文档命名、格式和模板以 `config.json` 为准；新增或调整文档类型时，同步维护 `doc-type/` 下对应格式的模板和配置映射。
- 文档版本规则和 `update.log` 格式以 `config.json` 为准；版本、索引和变更日志必须与文档实际内容一致。
- 写入前确保父文件夹存在（不存在则用 Write 前的目录操作创建）。
- 配置指定的索引文件是分类、定位和链接规范的依据，务必与磁盘实际文件保持一致；目录或文件移动后检查并更新所有受影响的链接。
- 遇到“覆盖确认 / 新文件夹名”等真正需要用户决策的点，才提问；其余情况直接执行。
