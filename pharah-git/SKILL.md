# 代码提交与推送规范（pharah-git）

统一约束 agent 提交、推送代码时的格式与行为。所有操作在当前 Git 工作树内进行，与具体仓库路径无关。

## 触发条件（何时启用本 skill）

仅当用户显式调用 `pharah-git`（通过技能选择器调用，或明确说“使用 pharah-git”）时启用。

仅提到提交、推送或提交信息，但未显式调用本 skill 时，不触发本流程。

## 指令

仅在用户显式调用本 skill 后，根据用户表达识别指令。以下关键词是常见表达，不要求固定命令格式：

| 指令 | 关键词 |
| --- | --- |
| **Mes / 生成提交信息** | `mes`、`message`、`msg`、生成提交信息、写提交信息、提交信息 |
| **Commit / 提交** | `commit`、提交、提交代码、提交改动 |
| **Push / 推送** | `push`、推送、推送代码、推送到远端 |

若用户只是在讨论关键词、意图不明确，或目标仓库/分支不清，不要执行变更，先澄清。

## 公共约束

- 仅当用户显式调用本 skill 后执行；写操作（提交、推送）仍需用户明确要求。
- 禁止 `--force`/`--force-with-lease`、禁止改写历史、禁止推送其他分支或 tags、不擅自切换远端或跟踪配置。
- 真需要用户决策的点（是否提交、是否修改提交信息、远端新更新如何处理）才提问；其余按流程直接执行。
- 命令失败时报告错误并中断，不丢弃或重置用户改动。

## Mes / 生成提交信息

查看当前分支的未提交改动，按下方内置模版生成提交信息并展示给用户。

**本指令只生成并展示，不执行 `git commit`、`git add` 或任何写操作。**

### 步骤

1. 确认当前位于 Git 工作树内（`git rev-parse --is-inside-work-tree`）；不在则说明原因并停止。
2. 收集未提交改动：`git status --short`、`git diff`（未暂存）、`git diff --cached`（已暂存）、`git diff --stat`；必要时查看未跟踪文件内容，以理解改动性质与涉及模块。
3. 逐项归纳改动，判定类型与主题：
   - **类型**：从下方允许集合中选一个最贴合改动性质的类型。
   - **主题**：改动所属模块/作用域（如 `pharah-git`、`goodsx`、`douyinpay`），无法判断时用最能概括的模块名。
4. 按模版生成提交信息：概述不超过 20 个中文字符，详细改动不超过 5 条。
5. 展示提交信息原文；无未提交改动时，告知用户无需生成。

### 模版

```
[类型][主题]:[20字以内中文概述]

[详细改动]：
1.xxxxx
2.xxxxx
```

- 第一行：`[类型][主题]:概述`，使用半角冒号 `:`；`[类型]`、`[主题]` 为字面方括号。
- 第一行与详细改动之间保留一个空行。
- `[详细改动]：` 使用全角冒号并单独成行，其下逐条列出，编号从 `1.` 起连续，每行一条。

### 规则

- **类型**（Conventional Commits 子集，取一个）：

  | 类型 | 含义 |
  | --- | --- |
  | `feat` | 新增功能 |
  | `fix` | 修复缺陷 |
  | `docs` | 文档变更 |
  | `style` | 格式/样式（不影响逻辑） |
  | `refactor` | 重构（不新增功能、不修缺陷） |
  | `perf` | 性能优化 |
  | `test` | 测试相关 |
  | `build` | 构建/依赖相关 |
  | `chore` | 杂项（脚本、配置、工具等） |
  | `ci` | CI 配置 |
  | `revert` | 回滚 |

- **概述**：中文，简短凝练，不超过 20 个字，概括本次改动的核心。
- **详细改动**：中文，逐条简短凝练，不超过 5 条；按重要性或逻辑顺序排列，只列实际改动，不臆造。
- 改动跨越多个主题时，主题取覆盖范围最大的模块；类型取影响最主要的一类。
- 除模版内容外，不添加多余段落、签名、`Co-authored-by`、emoji 或链接，除非用户明确要求。

### 示例

改动为当前仓库新增本 skill 时：

```
[feat][pharah-git]:新增提交信息生成指令

[详细改动]：
1.新增 pharah-git skill 定义
2.支持 mes 指令按内置模版生成提交信息
3.约束提交类型与主题的取值
```

## Commit / 提交

依次完成：确定提交信息 → 用户确认 → 提交前 `git pull` 校验 → `git commit`。

1. 确认当前位于 Git 工作树内；不在则说明原因并停止。
2. 查看当前分支未提交改动（`git status --short`）：无改动则告知用户无需提交并停止。
3. **确定提交信息**：
   - 若已有 `mes` 生成的提交信息（本次会话中已生成，或由用户直接提供），且仍与当前改动一致 → **直接使用**，不重复生成。
   - 否则先执行 **Mes / 生成提交信息** 生成一条。
   - 向用户展示提交信息，并询问是否需要修改；用户提出修改则按其意见调整，直至用户确认。
4. **用户确认后、提交前，先校验远端更新**：
   - 记录当前 `HEAD`：`git rev-parse HEAD`。
   - 检查当前分支是否配置 upstream：已配置时拉取当前分支的最新内容；未配置时视为仅有本地分支，跳过 `git pull` 并继续提交。
   - 拉取失败（含冲突）→ 报告错误并中断，不提交。
   - 拉取后 `HEAD` 发生变化（即带入了新的远端提交）→ **中断本次提交**，列出新拉取的提交并提示用户先核实更新，待处理后再重新发起。
   - `HEAD` 未变化（无新更新）→ 继续提交。
5. 暂存并提交：`git add -A` 后以确认后的信息执行 `git commit`。提交信息中的详细改动必须与本次实际暂存内容一致。
6. 报告提交结果（提交哈希、提交信息、分支）；失败时报告错误，不丢弃改动、不重置暂存区。

## Push / 推送

在 **Commit / 提交** 的基础上，提交成功后把当前分支推送到远端；远端若无该分支则新建。

1. 先完整执行 **Commit / 提交** 流程。
   - 提交流程被中断（如检测到远端新更新、拉取失败）→ 同步中断推送，不推送。
   - 本次无改动可提交，但当前分支已有尚未推送的本地提交 → 仍需继续推送（进入第 2 步）。
   - 既无新提交也无待推送内容 → 告知用户无需推送。
2. 确认目标：
   - 当前分支：`git rev-parse --abbrev-ref HEAD`。
   - 远端：优先使用分支已配置的 upstream 远端；无 upstream 时使用 `origin`。
   - 检查远端是否已有该分支：`git ls-remote --heads <remote> <branch>`。
3. 推送：
   - 远端已有该分支 → `git push`（或 `git push <remote> <branch>`）。
   - 远端无该分支 → 新建并建立跟踪：`git push -u <remote> <branch>`。
4. 禁止 force push、禁止推送其他分支或 tags、不切换远端、不改写历史。
5. 报告推送结果（远端、分支、是否新建）；失败时报告错误，不回滚已完成的提交。

---

## 注意事项

- 三个指令的写操作为递进关系：`mes` 只生成；`commit` = `mes`（或复用已有信息）+ 确认 + `git pull` 校验 + 提交；`push` = `commit` + 推送。
- 提交信息始终以用户最终确认为准；`mes` 生成的原始信息在用户修改后不保留。
- 展示提交信息后、以及提交前的 `git pull` 出现新更新时，都必须等待用户，不擅自继续。
